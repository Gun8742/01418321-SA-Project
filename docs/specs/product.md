# Product Specification

## เป้าหมายและขอบเขต

**Confirmed:** ระบบจัดการข้อมูลกลาง จัดชุดเอกสาร ตรวจความครบถ้วน เก็บหลักฐานการยื่น/ผลพิจารณา และยืนยันการรับเอกสารสำหรับการจ้างแรงงานต่างด้าว
กลุ่มผู้ใช้หลักคือนายจ้าง/ผู้กระทำการแทนและลูกจ้างต่างด้าว ไม่ใช่ระบบตัดสินอนุมัติของหน่วยงานรัฐ

รองรับข้อมูลการจ้าง, คำขอก่อนเดินทาง, Visa, การเดินทางเข้าเมือง, ใบรับรองแพทย์ และ Work Permit ตาม UC-01–UC-11
Login/logout, การดู/ดาวน์โหลดไฟล์, คำแจ้งข้อมูลไม่ตรง และสถานะผิดพลาดเป็น Supporting Flows ไม่เพิ่มเลข UC ธุรกิจ

ลำดับกระบวนการอยู่ใน [AGENTS.md](../../AGENTS.md#domain-rules); เงื่อนไขแต่ละกรณีอยู่ใน [Workflows](workflows.md)
หนึ่ง UC ไม่จำเป็นต้องเท่ากับหนึ่งหน้า หรือหนึ่งตาราง

## สิ่งที่ส่งมอบเป็นระยะ

1. **Frontend demo:** Routes และหน้าจอตาม Figma, forms/validation, fake-user context, Mock operations และ failure scenarios ตาม Contract; แสดงโหมดข้อมูลสมมติให้เห็นเสมอ
2. **Integrated application:** Operations ฝั่ง Server, Authentication ที่ตรวจแล้ว, record-level authorization, PostgreSQL, Private Storage, migrations และ tests ที่เกี่ยวข้อง
3. **พร้อมสาธิต:** มีชุดข้อมูลสมมติและขั้นตอน reset ที่ชัดเจน; Happy path และ recovery ผ่าน Acceptance โดยไม่ใช้ข้อมูลบุคคลจริง

การทำ Spec ไม่อนุญาตให้เริ่มพัฒนา Deploy หรือ merge PR นี้โดยอัตโนมัติ

## ขอบเขตภายใน v1

- จัดการลูกจ้างและ Employment โดยใช้นายจ้างที่บัญชีมีสิทธิ์ ไม่เปิดให้ผู้ใช้สร้างสิทธิ์ของตนเอง
- จัดชุดและ Checklist ตามกรณี เลือกเอกสารเดิมหรือแนบเพิ่ม; แสดงข้อมูลประกอบแม่แบบและ preview สำหรับตรวจทาน
- บันทึกการยื่นและผลจริงจากหน่วยงาน แยกผลอนุมัติ/เอกสารพร้อมใช้/การรับเอกสาร
- ติดตามผลคำร้องเดิมและส่งเอกสารเพิ่มในคำร้องเดิม
- รับไฟล์หรือรายละเอียดช่องทางรับจริง และบันทึก Receipt เมื่อยืนยันจริง
- บันทึกการเดินทาง/ตรวจสุขภาพพร้อมหลักฐานตามสิทธิ์ที่กำหนดใน Authorization
- คำแจ้งข้อมูลบันทึกไม่ตรงมีสถานะติดตาม โดยไม่แก้ผลตัดสินหรือเอกสารต้นฉบับเอง

## นอกขอบเขตที่ยืนยันตอนนี้

- API เชื่อมสถานทูต/กรมการจัดหางาน/ตม./โรงพยาบาล, การอนุมัติอัตโนมัติ และการวินิจฉัยทางการแพทย์
- Public sign-up, self-service role assignment, password-reset UI, admin portal, payment และ notification email/SMS
- OCR/AI ตรวจความถูกต้องทางกฎหมาย, digital signatures, automatic issuance และ generation ของแบบราชการที่ยังไม่มี template ยืนยัน
- Dashboard เชิงสถิติ/รายงานใหม่ที่ไม่มี UC, audit-history UI และ workflow ครบวงจรสำหรับเจ้าหน้าที่ภายนอก
- สิทธิ์ AUTHORIZED_OFFICER ที่ ER กล่าวถึงยังไม่ใช่สิทธิ์ใช้งานแบบไม่มีขอบเขต

Q44/Q45 ใน ER เป็นแนวทาง provisioning/credential maintenance ไม่ใช่เหตุผลให้เพิ่ม registration/reset flow โดยไม่มี Requirement

## ข้อมูลต้นทางและความขัดแย้ง

- revised Description เป็นเจ้าของเป้าหมาย Actor และพฤติกรรม; Sequence ใช้ trace การประสานงาน แต่ไม่ถือเป็น SQL ที่พร้อมรัน
- Figma กำหนดหน้าตา ลำดับการนำเสนอ และ screen IDs; ปุ่มเปลี่ยนตัวอย่างใน Prototype ไม่ใช่ production action
- ER/Dictionary เป็นแบบข้อมูลเสนอ; การขาดคอลัมน์ไม่ตัด Requirement ทิ้ง และ NOT NULL ที่ขัด lifecycle ต้องตัดสินใจก่อน migration
- หนังสือ/แม่แบบและ Checklist ต้องตรงประเภทคำขอ/หน่วยงานตามเอกสารที่ทีมให้ ไม่มีการอ้างว่าใช้ได้กับแรงงานทุกประเภทหรือทุกสัญชาติ
- ประเด็นที่ต้องยืนยันและเงื่อนไขส่งมอบอยู่ใน [Decisions](decisions.md); ไม่ใช้ default implementation กลบข้อมูลที่หาย

## ข้อกำหนดทั่วไป

ใช้ภาษาไทยและ Technical Terms ตามแบบ; UI แจ้งสาเหตุที่ผู้ใช้แก้ได้โดยไม่เผยข้อมูลของผู้อื่น
เก็บวันที่ราชการตามหลักฐาน ไม่เดาวันที่ขาด; วันของธุรกิจแยกจาก timestamp ของระบบตาม Contract
ข้อมูลทดสอบเป็นข้อมูลสมมติทั้งหมด; การผ่าน Mock ไม่ถือว่าทดสอบสิทธิ์หรือความปลอดภัยฝั่ง Server แล้ว
